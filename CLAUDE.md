## What this is

"Hanabiの小天地" — a static, single-page personal website (vocabulary quiz app, guestbook, about page) in Traditional Chinese with 9-language i18n (zh/zh-Hans/en/ja/ko/ru/fr/es/de), focused on vocabulary review and language learning. No framework, no build step, no bundler, no package.json. Plain HTML/CSS/JS served directly. Satellite sites (`世界計畫-花火網頁`, `鳴潮-花火網頁`, `osu-花火網頁`) are separate repos and no longer linked from here.

## Architecture (overview)

- **Single-page shell**: `index.html` holds every page as a sibling `<div id="page-…">`; `switchPage(page, el)` in `js/quiz.js` shows one (clears its inline `display`, sets `body[data-page]`, marks `.nav-btn[data-tab]` copies active). No router, no URL state. Desktop header: controls row, brand, `.main-nav` (首頁 / 單字測驗 / 複習 / 學習 ▾ / 工具 ▾) and the ☰ menu; phones (≤768px) use the bottom `.tabbar` and the 學習 / 更多 sheets. Full detail: `.claude/rules/ui-shell.md`.
- **Files**: CSS split by feature in `css/*.css`, each linked in `<head>`; JS as plain `<script>` tags at the end of `<body>` in dependency order (theme → mascot → PapaParse CDN → `js/i18n.js` → the 9 `i18n/<lang>.js` → speech → quiz → learnlang → path → home → practice → account → dict → alphabet data → alphabet → grammar → reading → listening → updates → tour → rails → guestbook → notes → feedback → widgets). **New JS files go in that script list and in `service-worker.js`'s `ASSETS`; new CSS files in `<head>` and `ASSETS`; bump `CACHE_NAME` when `ASSETS` changes.**
- Everything is global functions/variables; markup calls them with `onclick="…"`. No modules.
- Progress lives in `localStorage`; write it with `storeSet(key, value)` (js/quiz.js). Keys worth keeping across devices go in `SYNC_KEYS` with a merge rule (`.claude/rules/account-social.md`).
- Built data is generated by scripts in `tools/` — **don't edit `data/vocab/`, `data/grammar/`, `data/reading/`, `data/listening/` or `data/audio/` by hand**; fix the source / script and rebuild (each rule file says how).
- Shown changes need an entry in `js/updates.js` (`SITE_UPDATES`, all 9 languages) at push time; a new main feature also gets a site-tour step (`js/tour.js`, 9 languages).

**i18n (`js/i18n.js` + `i18n/<lang>.js`)**: `js/i18n.js` only declares `const I18N = {}` plus the shared logic (`applyLang`, `setSiteLang`, `t`); the actual translations live in one file per language — `i18n/zh.js`, `i18n/zh-Hans.js`, `i18n/en.js`, `i18n/ja.js`, `i18n/ko.js`, `i18n/ru.js`, `i18n/fr.js`, `i18n/es.js`, `i18n/de.js` — each just assigning a flat dict to `I18N.<lang>` (e.g. `I18N.en = {...}`; Simplified Chinese needs bracket syntax, `I18N['zh-Hans'] = {...}`). `zh-Hans.js` was generated from `zh.js` with OpenCC (`tw2sp`) and then hand-fixed for mainland wording (单词, 复制, 置顶, 离线, 导航栏, Google 表格…) — when adding a zh key, write the Simplified version by hand in the same style rather than a character-by-character conversion. These must load as `<script>` tags *after* `js/i18n.js` (which declares `I18N`) and *before* any script that calls `t()`/`applyLang()` at top level. `applyLang(lang)` walks all `[data-i18n]` / `[data-i18n-placeholder]` elements and swaps text/placeholders; `t(key, params)` is used for dynamically-generated strings (e.g. `t('load_success', {n: 5})`, using `{n}`-style placeholder substitution). Adding UI text means adding the key to **all 9** `i18n/<lang>.js` files. `setSiteLang()`/`applyLang()` persists choice to `localStorage['site_lang']` and calls `refreshDynamicContent()` (in `js/quiz.js`) so already-rendered dynamic content (quiz menus) re-renders in the new language.

## Look and layout

- **Theme "和紙" (light) / "墨夜" (dark)** via `data-theme` on `<html>` (`js/theme.js`): flat paper, ink text, one vermilion accent, Noto Serif TC headings / Noto Sans TC body; no glows, gradients or glassmorphism. Colours are CSS custom properties in `css/theme.css` — use the semantic tokens (`--primary`, `--primary-edge`, `--surface`, `--line`, `--edge`, `--ink`, `--success*`, `--danger*`, `--track`, `--font-serif`), never hardcoded colours, and check both themes. Buttons are **chunky 3D** (2px outline + `box-shadow: 0 4px 0 var(--edge)`, `:active` moves down 4px); the shared recipe is at the top of `css/quiz.css`.
- Controls use the line icons of `uiIcon(name)` (js/quiz.js), not emoji; text at least 12px; touch targets 44px on `pointer: coarse`. A page's one-line intro uses `introHtml` / `introInfoBtn` (js/quiz.js).
- **Desktop layout rule (owner, 2026-10-23)**: if a page needs scrolling on a computer to show all of it, widen it to 1180px (`body[data-page]` rules in css/base.css, rail breakpoints in css/rails.css) or split it into left / right columns at ≥1024px; phones keep one column. Measure new content in the browser yourself before reporting.
- **Phone layout (≤768px)**: `main` has a 16px gutter and a page's outer card loses its frame (css/responsive.css); uneven button groups become even grids.
- Chinese (Traditional) is the default/fallback language (`I18N.zh` in `t()`). Old markup uses HTML entities (`&#x...;`) for CJK text; new text can be plain UTF-8.

## Workflow for feature/dev requests

For any non-trivial dev request, work through these stages in order:

1. **UI/design pass** (only if the request touches the front end): match the 和紙/墨夜 theme — flat cards, chunky 3D buttons, the CSS custom properties in `css/theme.css` (don't hardcode colors; check both themes), the phone layout (≤768px: bottom tab bar, no top nav), and the existing per-feature `css/*.css` split. There's no React/Tailwind/v0 in this project — new UI is plain HTML + CSS, written by hand.
2. **Implementation**: wire up the HTML/CSS/JS following the conventions above (global functions, `onclick=` handlers, i18n keys added to all 9 `i18n/<lang>.js` files, new files registered in `index.html`'s script/link tags and `service-worker.js`'s `ASSETS`).
3. **Verification** (this project has no test suite or build step, so "testing" means): check the changed files for obvious syntax errors, then actually load the change in a browser (e.g. `python -m http.server` from the repo root) and click through the affected feature before calling it done — per the top-level guidance to verify UI changes in a real browser rather than assuming they work.
4. **Final report**: once verified, and after committing/pushing per the user's request, give a short summary of what changed — don't pad it with restated context.
