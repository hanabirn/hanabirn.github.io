# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Hanabiの小天地" — a static, single-page personal website (vocabulary quiz app, guestbook, about page) in Traditional Chinese with 9-language i18n (zh/zh-Hans/en/ja/ko/ru/fr/es/de), focused on vocabulary review and language learning. No framework, no build step, no bundler, no package.json. Plain HTML/CSS/JS served directly.

## Running / deploying

There is no build or test command — the repo root is served as-is by **GitHub Pages**.

- The remote is `github.com/hanabirn/hanabirn.github.io` (a GitHub Pages *user site*), served at the custom domain **`https://hanabirn.xyz/`** straight from the `main` branch root. Pushing to `main` is the deploy — there is no CI workflow, no build step, and no `.github/` directory.
- The custom domain is set by the `CNAME` file at the repo root — don't delete or rename it, or GitHub Pages drops the domain. `hanabirn.github.io` 301-redirects to `hanabirn.xyz`, so old links still work. DNS lives in Cloudflare (GitHub's four apex A + four AAAA records) with the **proxy deliberately off**: behind Cloudflare's orange cloud GitHub can't complete its HTTPS certificate challenge.
- Absolute URLs that name the host — the canonical link and OG/Twitter meta tags in `index.html`, `sitemap.xml`, `robots.txt` — use `https://hanabirn.xyz/`. Use that domain (not `hanabirn.github.io`) for any new absolute URL.
- Because the site is served from the domain root, absolute paths (`/icons/...`, `manifest.json`'s `start_url: "/"`) work as-is; no base-path rewriting is needed.
- The site used to be on Netlify (`hanabirn.netlify.app`), which is now paused for exceeding its free usage limits. All Netlify config (`netlify.toml`, the empty `netlify/functions` dir, the local `.netlify` CLI cache) was removed in the 2026-09-24 cleanup, along with the stale `hanabirn.netlify.app` URLs in `index.html`'s OG/Twitter meta tags. Don't reintroduce Netlify-specific files or URLs — with one deliberate exception: Netlify built `hanabirn.netlify.app` from this repo's `main` (since 2026-10-08 its builds are **Stopped** in the Netlify dashboard so pushes don't use its free credits — the last deploy, with `_redirects`, keeps serving; changing `_redirects` means switching builds back to Active first), and visitors kept using it (an iPhone home-screen app installed from there got 403 from the AI Worker, which only allows `hanabirn.xyz`), so the root `_redirects` file 301s every path there to `https://hanabirn.xyz/…?from=netlify` (added 2026-10-03 at the owner's request); that marker makes `js/widgets.js` show the "網站搬家囉" notice (`#moved-overlay`: delete the old home-screen app and install again, offering `openInstallHelp()`) and is then removed from the address bar. Progress stored under the Netlify origin can't follow; the notice says so. GitHub Pages runs Jekyll, which skips `_`-prefixed files, so it has no effect on the real site.
- There is no linter or test suite configured.

## Architecture

**Single-page app shell**: `index.html` contains every "page" (`#page-home` — the default — plus `#page-quiz`, `#page-examquiz`, `#page-notes`, `#page-about`, `#page-guestbook`, `#page-feedback`) as sibling `<div>`s toggled via `display: none/block`. `switchPage(page, el)` in `js/quiz.js` handles navigation — no router, no URL state. Every page has a `.nav-btn[data-tab=…]` in the desktop `.main-nav` **and** in the phone UI (bottom `.tabbar` for home/quiz/exam/notes, the "More" bottom sheet for dict/alphabet/guestbook/feedback/about, plus 更新內容, the tour replay, settings and reload); "關於我" is not in the desktop nav but a `.header-btn` in the header, next to "更新內容" (`js/updates.js`: the `SITE_UPDATES` changelog popup, `UPDATES_PER_PAGE` (4) entries a page with 上一頁 / 下一頁 and ← → — add an entry in all 9 languages when shipping something visible; a dot shows until it's opened). On phones both header buttons are hidden and live in the More sheet. `switchPage()` sets `.active` by `data-tab`, not on the clicked element, so all copies stay in sync, and tab visibility (`applyTabVisibility`) hides every copy. It shows a page by clearing its inline `display` (not setting `block`, so a page's CSS can make it a grid) and puts the page on `body[data-page]`; `css/base.css` uses that to widen the alphabet, dictionary and quiz pages to 1180px on screens ≥1024px (on the quiz page only `#path-card` takes the width). Desktop layouts there: the alphabet shows 6 cards a row (kana as a 5-column 五十音 chart with `.alpha-blank` gaps), the dictionary is a 2-column grid (`#dict-results` is `display: contents`; examples on the right), and the path shows the picked unit's levels beside a sticky unit list (`.path-wide`; phones keep the `<details>` accordion, `.path-accordion`). Home is locked visible. There is no guide page any more: new visitors get the tour below. All CSS is split by feature into `css/*.css` and all linked individually in `<head>` (no bundling), and `js/*.js` files are loaded as plain `<script>` tags in a specific dependency order at the bottom of `<body>` (theme → mascot → PapaParse CDN → `js/i18n.js` → the 9 `i18n/<lang>.js` dictionary files → speech → quiz → path → home → practice → account → dict → alphabet data → alphabet → grammar → updates → tour → rails → guestbook → notes → feedback → widgets). New JS files must be added to that script list, to `service-worker.js`'s `ASSETS` cache list, and CSS files to both `<head>` and `ASSETS`.

**i18n (`js/i18n.js` + `i18n/<lang>.js`)**: `js/i18n.js` only declares `const I18N = {}` plus the shared logic (`applyLang`, `setSiteLang`, `t`); the actual translations live in one file per language — `i18n/zh.js`, `i18n/zh-Hans.js`, `i18n/en.js`, `i18n/ja.js`, `i18n/ko.js`, `i18n/ru.js`, `i18n/fr.js`, `i18n/es.js`, `i18n/de.js` — each just assigning a flat dict to `I18N.<lang>` (e.g. `I18N.en = {...}`; Simplified Chinese needs bracket syntax, `I18N['zh-Hans'] = {...}`). `zh-Hans.js` was generated from `zh.js` with OpenCC (`tw2sp`) and then hand-fixed for mainland wording (单词, 复制, 置顶, 离线, 导航栏, Google 表格…) — when adding a zh key, write the Simplified version by hand in the same style rather than a character-by-character conversion. These must load as `<script>` tags *after* `js/i18n.js` (which declares `I18N`) and *before* any script that calls `t()`/`applyLang()` at top level. `applyLang(lang)` walks all `[data-i18n]` / `[data-i18n-placeholder]` elements and swaps text/placeholders; `t(key, params)` is used for dynamically-generated strings (e.g. `t('load_success', {n: 5})`, using `{n}`-style placeholder substitution). Adding UI text means adding the key to **all 9** `i18n/<lang>.js` files. `setSiteLang()`/`applyLang()` persists choice to `localStorage['site_lang']` and calls `refreshDynamicContent()` (in `js/quiz.js`) so already-rendered dynamic content (quiz menus) re-renders in the new language.

**Word sets (`data/vocab/*.json`, built by `tools/build_vocab.py`)**: the quiz, paths, flashcards and listening tool load bundled, graded word lists — `en_jh` / `en_sh` (大考中心 7000 Level 1–2 / 3–6), `en_toeic` (TSL), `en_toefl` (ECDICT toefl tag minus the 國中 words), `jlpt_n5`…`jlpt_n1` and `topik_1`…`topik_4` (the owner's own sheets), `hsk_1`…`hsk_7` (HSK 3.0, Nov-2025 revision; 7 = 7–9). Each list is ordered easy-first by frequency, which is what makes the first path levels easy. The **topic sets** `tp_<ja|ko|en|zh|fr|ru>_<topic>` (10 topics × 40 words = 4 levels each: greetings, food, home, shopping, transport, travel, weather, school, work, health; added 2026-10-04, French and Russian 2026-10-08 — French rows `le chat<TAB>m.<TAB>zh<TAB>en` like the CEFR sets, Russian `слово<TAB>сло́во<TAB>zh<TAB>en`) are the exception: hand-written by Claude, approved by the owner, in `tools/topics/<lang>.tsv` (`## <topic>` headers, `word<TAB>reading<TAB>meaning<TAB>english`, edit those files directly) and kept in the file's order; `build_vocab.py --only topics` turns them into JSON. **French and Russian** are graded by CEFR, A1–C1, on the exam page: `fr_a1`…`fr_c1` from FLELex (the "Beacco" version, which gives every lemma a level; replaced the owner's French sheet — `fr` is now in `LEGACY_SET_IDS`) and `ru_a1`…`ru_c1` from the Russian Kelly list. Both lists lack translations, so `build_vocab.py --only fr|ru` (needs `pip install xlrd` for Kelly's .xls) streams Wiktionary's kaikki.org dump (≈0.6 / 0.9 GB, never saved — only the entries for listed words go into `tools/.vocab-cache/kaikki_<lang>.json`; Russian is matched with ё folded to е because Kelly writes еще) for English glosses, French genders and Russian stress marks, and has **Gemini** write the Chinese meanings (`gemini_meanings`: batches of 100 with a JSON schema, cached in `tools/.vocab-cache/gemini_<lang>.json`, so a re-run only asks for new words; it uses the assistant's key from `worker/assistant/.dev.vars` but only models the assistant doesn't — `GEMINI_MODELS` — because quotas are per model; when the free quota runs out it stops and the next run carries on). Fix a bad meaning in `ZH_FIX_FR` / `ZH_FIX_RU` (also used for words Gemini can't translate alone: articles, clitics) and, when Wiktionary picked a homonym, the English in `EN_FIX_FR` / `EN_FIX_RU`; drop list noise (names, forms filed as words) in `FR_SKIP`. A re-run with everything cached makes no Gemini calls. Kept: words Wiktionary knows in that part of speech, French nouns only with a gender, each word once at its lowest level, most frequent first. French rows are `[le chat, m., zh, en]` (article added except before h, months and days; the gender is the reading), Russian `[молоко, молоко́, zh, en]` (the stressed form as reading). `isFrenchQuizLang()` / `isRussianQuizLang()` cover them; `wordSetName()` names them "法文 A1"; the exam page's `#examquiz-cefr-level-card` is filled by `showCefrLevels(lang)`; the quiz page's 法文 / 俄文 buttons open their topics like the other languages, whose link (`topic_exam_fr` / `topic_exam_ru`) leads there. Listening typing accepts a French noun without its article and Russian without ё. Chinese (`zh.tsv`) is written as `traditional<TAB>pinyin<TAB>english[<TAB>simplified]` in Taiwan wording and readings: the script converts simplified with OpenCC `tw2s` (character by character, so 計程車 → 计程车, not 出租车) unless the 4th column gives it, and bopomofo from the space-separated pinyin with `pypinyin`, giving HSK-shaped rows. **Don't edit the JSON by hand** — fix `tools/build_vocab.py` and re-run it (`pip install wordfreq opencc-python-reimplemented pdfplumber pypinyin`; sources are cached in the git-ignored `tools/.vocab-cache/`; `--offline` reuses the cache; JLPT/TOPIK are re-fetched from the owner's Google Sheets, so editing those sheets means re-running the script). English Chinese meanings come from ECDICT via `zh_meaning()`, which drops computing-jargon senses and moves function-word / common-adverb senses first; `ZH_OVERRIDES` patches the few words it still gets wrong. Sources and licences: `data/vocab/README.md`; each path card credits its list (`path_source`). In `js/quiz.js`, `BUNDLED_SETS` maps set → row kind, `WORD_SET_FAMILIES` groups sets by language for the pickers, `QUIZ_LANG_ORDER` is derived from it, and `loadWordSet(id)` is the one loader (French alone is still read from its Google Sheet, `SHEETS.fr`). `selectWordSet(id)` opens a set. The 單字 (quiz) page is topic-based and the 檢定 (exam) page level-based: `selectLanguage()` sends every language (日/韓/英/中/法/俄) to `#topic-card` (`showTopicPicker` / `renderTopicPicker`: a tile per topic with its path progress, plus a link to that language's levels on the exam page, `topicToExam`). English 國中/高中/多益/托福 all sit on the exam page's English card. `TOPIC_IDS` / `TOPIC_EMOJI` / `TOPIC_FILE_LANG` / `topicOf()` describe the topic sets (they are added to `BUNDLED_SETS` and, after the graded sets, to `WORD_SET_FAMILIES`); show a set's name with `wordSetName(id)` ("日文・吃飯" for a topic, else `t('quiz_<id>')`), never `t('quiz_' + id)` directly. `backToLanguage()` returns a topic set to its topic card. The retired general sets (`jp`, `kr`, `en`, `zh`) remain in `LEGACY_SET_IDS` so their mistake-book entries still show. Flashcards pick language + display mode, then a deck (word set); listening picks everything on one page (see Practice tools below); flashcard known/unknown marks stay keyed by language (`lang|mode|word`). Use `isEnglishQuizLang()` (never `=== 'en'`) for English checks. Path progress lives in `path_progress_v2` (reset when the sets were re-ordered).

**Vocabulary quiz (`js/quiz.js`, the largest file)**: the quiz engine. A pasted custom Google Sheet URL still goes through `loadSheetData` and the per-language `parseX(rows)` functions (fixed-width row "stride" parsing — see `parseJapanese`/`parseJapanese2`). Quiz state (mode, current word, score, shuffled order) lives in module-level `let` variables, not a framework state store. Scoring is +10 right, −3 wrong, floored at 0. Mistakes, quiz history, and flashcard "known" words persist to `localStorage` (`quiz_mistakes`, `quiz_records`, `flashcard_known`). Write progress with `storeSet(key, value)` (top of `js/quiz.js`), not a bare `localStorage.setItem`: when the ~5 MB quota is full it drops the re-downloadable `quiz_cache_*` word-list copies (biggest first, keeping the current set) until the write fits, so progress is never silently lost and a result screen never throws. Every answer goes through one path in `selectOption()`: grade the SRS card, a miss → `addMistakeEntry()`, a hit → `noteMistakeCorrect()`. A mistake is **repaired** after `MISTAKE_FIX_STREAK` (2) right answers in a row (`entry.fix`; a miss or a timeout resets it); it then gets `fixedAt`, stays in the book struck through for `MISTAKE_FIXED_KEEP_DAYS` (30) and returns to the list if missed again. Badges and home count only open ones (`getActiveMistakes()`). Per-session extras live there too: `comboNow`/`comboBest` ("連對"), `sessionStartedAt`, both reset when a session asks question 1. Show a quiz-page card with `showOnlyQuizCard(id)` (`QUIZ_PAGE_CARDS` lists them all) rather than toggling cards one by one. Score-card sharing renders a `<canvas>` and exports as an image.

**Spaced repetition (`srs_quiz`, in `js/quiz.js`)**: every answered quiz question (any word set, including JLPT/TOPIK/HSK) and every mistake-review answer grades a Leitner card via `gradeSrsQuizCard(entry, correct)` — right moves it up a box (intervals `SRS_INTERVAL_DAYS` = 0/1/3/7/14/30 days), wrong drops it to box 1 due in 10 minutes; a timer timeout counts as wrong. Cards use the **same shape and id as mistake-book entries** (`quizEntryFor(type, answer)` → `{id: lang|word|group, lang, word, answer, hint, group, zct}`), which is what lets the review run on the mistake-review engine: `startSrsQuizReview()` sets `reviewMode = true` with `reviewSource = 'srs'` (vs `'mistakes'`) and up to `SRS_REVIEW_LIMIT` (20) due cards mixed across sets; `nextQuestion()`'s review branch fills wrong options from the same set's cards, then that set's `quiz_cache_<set>`, then near-miss kana for readings. The quiz page's "間隔複習" tool first opens the `#srs-card` page (due count, next batch, 7-day forecast, cards per stage; `startSrsQuizReview('tool')`, whose "返回" comes back there); the home dashboard starts the review directly and "返回" goes home. Anything that starts a new word set must clear the review state (`endReviewState()` in `selectLanguage`/`selectExamSet`), because `showModeSelection()` treats a lingering `reviewMode` as "go to the mistake book". The old flashcard-only SRS (`srs_cards`) was removed in phase 2 of the 2026-10 redesign; its data is simply ignored.

**Satellite sites (no longer linked from here)**: `世界計畫-花火網頁`, `鳴潮-花火網頁`, and `osu-花火網頁` are separate standalone sites/repos in the same family. This site used to host an outbound-links page ("遊戲區") pointing to them, but that page was removed to keep the site focused on vocabulary review and language learning — the satellite sites and their repos are unaffected and still deployed independently.

**Guestbook (`js/guestbook.js`, Worker side `worker/assistant/src/guestbook.js`, rebuilt 2026-10-08)**: served by the `hanabi-assistant` Worker at `/guestbook` (`GUESTBOOK_API`; `localhost:8787` locally) and stored in its KV namespace `GUESTBOOK` (`list` = all messages newest first, `u:<uid>` = that account's message), which only the Worker can write — so the rules really hold. Posting needs a site account: the client sends the Firebase ID token, the Worker checks it with the Identity Toolkit (`FIREBASE_API_KEY`, the public web key), refuses email accounts whose address isn't verified (the gate offers 寄驗證信 via `sendEmailVerification`), allows **one message per account** (the mark stays even if the owner deletes the message) and has Gemini (`moderate()`, lite model first, JSON schema) refuse violence, politics, sexual content, hate, spam/ads and personal data — failing closed (`moderation_busy`) when no model answers. Friendly mentions of a country ("台灣加油") are explicitly not politics. `renderGuestbookGate()` shows sign in / verify / already posted / the form; `account.js` calls `guestbookOnUser()` on sign-in changes. The owner deletes a message with `DELETE /guestbook/<id>` + `Authorization: Bearer <ADMIN_TOKEN secret>`. The old Apps Script guestbook (5 messages) was imported into KV; the 建議&改進 page still uses Apps Script.

**Home dashboard (`js/home.js` + `css/home.css`)**: `renderHome()` fills `#page-home` from data `js/quiz.js` already keeps in localStorage — `daily_activity` (`{'Y-M-D': words practised}`, bumped by `logDailyActivity()` on every answered quiz/listening question and every rated flashcard, pruned to 120 days), `calcStreak()` (a day counts if a quiz was finished *or* any word was practised), `last_quiz_set` (set by `startQuiz()`, drives "繼續學習"), `srs_cards`, `quiz_mistakes` and `quiz_records`. The only home-specific key is `daily_goal` (10/20/30/50, cycled by tapping the ring). It re-renders on load, on opening the page and on language switch (`refreshDynamicContent`). To jump into the quiz page from home, `homeResetQuizPage()` clears `currentLang` *before* calling `backToLanguage()` — otherwise a previous JLPT/TOPIK/HSK session makes it bounce to the exam picker.

**Practice tools (`js/practice.js` + `css/practice.css`, redesigned 2026-10)**: the screens around the quiz engine. `renderPracticeHub()` draws the 練習中心 grid under the language buttons (`#quiz-tools`): a tile per tool with what's waiting (due SRS cards, open mistakes, known flashcards, last listening score, words this week) and a 小花火 suggestion for the most urgent; it re-renders via `updateMistakeBadge()` and `refreshDynamicContent()`. The mistake book (`renderMistakeBook`) is a ruled notebook with per-set chips, sort by most-missed / recent / repaired, red dots for times missed and two repair slots; "修復" (`startMistakeRepair`) runs up to 10 open mistakes on the review engine with `reviewSource = 'mistakes'`, re-asking each right answer once more a few questions later (`requeueForRepair`) so one round can repair a word. The stats page shows how much is learned (the best SRS box per word, grouped into 4 stages `SRS_STAGES`: 新學 1 / 學習中 2–3 / 熟悉 4 / 精通 5–6, per word set against its cached word count), a 16-week practice calendar from `daily_activity`, this week vs last week, achievements and recent quizzes. Flashcards: a deck list (`renderFlashcardDecks`, prefs in `flashcard_prefs`) → a 20-card session (the set's 還不熟 words, then unseen ones in list order, topped up with known ones) on a card you flip by tap/space and rate by swiping (pointer events, `FC_SWIPE_PX`) or ← →. The result screen pieces (`resultHeroHtml`, `resultGoalHtml`, `resultHookHtml`) are shared by `showResults()` and the flashcard finish: confetti + 小花火, accuracy / best streak / time, the daily-goal ring, and a reason to come back (cards due now / within 24 h / next batch); "再練錯的字" (`retryWrongWords`) replays the session's misses as a repair round. The listening quiz (in `js/quiz.js`) has a one-page setup remembered in `listening_prefs`, a big play button with 🐢 slow (`speakText(…, {slow})`), and two ways to answer: `choice` (four look-alikes: near-miss kana for Japanese, same-first-letter words otherwise) or typing with letter boxes, a hint that reveals a character for 2 points, and a small-kana key row; a missed word goes to the mistake book as the entry `lessonEntryFor()` builds.

**Accounts & sync (`js/account.js` + `css/account.css`, added 2026-10-04)**: optional sign-in (Google popup, or email + password with sign-up / reset) through Firebase project `hanabi-site` (Spark plan; Auth providers Google + Email/Password; authorized domains include `hanabirn.xyz` and `localhost`; Firestore in `asia-east1` with owner-only rules `match /users/{uid}/{document=**} { allow read, write: if request.auth.uid == uid }`). The web config in `FIREBASE_CONFIG` is public by design. Only the Auth SDK is loaded (dynamic `import()` from gstatic, pinned version in `FIREBASE_SDK`), and only when the account dialog opens or `localStorage.acct_signed_in` says this device was signed in; Firestore is used through its REST API with the user's ID token (`fsRequest`) instead of the 680 KB SDK. Each key in `SYNC_KEYS` is one document `users/{uid}/data/{key}` = `{v: <localStorage string>}`, merged with its own rule (`syncMerge`: unions / newer entry / max, scalars keep this device's value) — on sign-in for every key (`acctFullSync`), afterwards for keys written since (a wrapped `Storage.prototype.setItem` marks them; uploaded `SYNC_DEBOUNCE_MS` after the last change and when the page is hidden). Not synced: 記事本, `quiz_cache_*`, device prefs. Add a key to `SYNC_KEYS` (with a merge rule) when a new feature stores progress worth keeping. Sign-out keeps the device's data; "delete account" removes the cloud docs and then the user (needs a sign-in within the last few minutes). UI: `.account-entry` in the header and the phone More sheet, `#home-account-card` (hidden when signed in), `#account-overlay`. Explained to visitors in privacy.html section 4 (`sa_*` keys in js/privacy.js).

**Learning path (`js/path.js` + `css/path.css`)**: every built-in set (`QUIZ_LANG_ORDER`) opens on a path once loaded (`showSetStart()`; a pasted custom sheet still goes straight to the mode picker). The set is cut **in sheet row order** into levels of `LESSON_SIZE` (10) words, units of `LEVELS_PER_UNIT` (10) shown as `<details>`; inserting rows mid-sheet therefore shifts later words between levels. A level = word preview (`#lesson-card`) then a quiz asking each word once, run on the same review engine as SRS with `reviewSource = 'lesson'` (`lessonEntryFor()` builds entries with the same id/shape as `quizEntryFor()`: JP kanji words → reading, Chinese → English meaning with pinyin hint, else meaning in English when the UI isn't Chinese), so lesson answers also grade SRS cards and wrong ones go to the mistake book. `LESSON_PASS_PCT` (80) unlocks the next level; progress is `localStorage.path_progress = {setId: {done, best}}` (`done` = levels passed in a row). quiz.js hands lesson results/again/back to `lessonResultHtml()` / `lessonAgain()` / `lessonBack()`; "自由練習" (`showFreePractice`) is the old mode picker, whose "返回" (`modeCardBack`) returns to the path.

**Dictionary (`js/dict.js` + `css/dict.css`, `#page-dict`)**: no backend and no keys — three CORS-enabled services called from the browser, each rendering its own section so one failing never blanks the others; a new search aborts the previous one (`AbortController`). Wiktionary REST `page/definition/{word}` gives part of speech + **English** definitions grouped by language code (try the word as typed, then lower-case, then Capitalised — titles are case-sensitive); its HTML is reduced to text via `DOMParser` after dropping `<style>` blocks. Tatoeba `/unstable/sentences` (requires `sort`) gives example sentences with a translation into the site language. MyMemory is a translation memory that mistranslates lone words (食べる → 美食), so the headline translation is the first Wiktionary gloss translated from English (to eat → 吃); only words Wiktionary lacks (many Chinese ones) are sent to MyMemory directly. MyMemory allows ~5,000 chars/day per visitor IP. Attribution for all three is in the page footer (`dict_sources`). Phones reach the page from the "More" sheet. `escHtml()` also escapes `"` because dictionary output goes into `data-*` attributes.

**Alphabet chart (`js/alphabet.js` + `js/alphabet-data.js` + `css/alphabet.css`, `#page-alphabet`)**: a beginner letter chart with tabs for English, hiragana, katakana (both with dakuon / handakuon), Korean (basic + double consonants, basic + compound vowels), 注音 (with pinyin), Russian, French, German (+ Ä Ö Ü ß) and Spanish (+ Ñ). Every entry in `ALPHABETS` is `[glyph, reading, text to speak, example word, word reading, emoji, meaning zh, meaning zh-Hans, meaning en]`, hand-written — edit the data file directly. The text to speak is not always the glyph: Korean consonants say their name and then their sound with ㅏ ("기역, 가"), vowels the vowel syllable (아), 注音 symbols a character with that sound (ㄅ → 玻), Russian/Spanish letters their names, because TTS reads lone symbols unreliably; English/French/German letters are spoken in lower case (French Y as "i grec"), because phone voices read a lone capital as "capital A" / "A majuscule". An empty example word marks a letter that is basically unused (ヂ, ヅ, ヲ). Meanings are only stored in zh / zh-Hans / en (other UI languages get English) and are hidden when the UI language is the tab's own language. `alphaHighlight()` marks the letter inside the example word. Sound goes through `speakText()` (see Speech below). Reached from the desktop nav, the phone "More" sheet and the home page's "剛開始學？" button; the chosen tab is kept in `localStorage['alpha_tab']`.

**Speech (`js/speech.js`)**: every 🔊 on the site — quiz `speakWord()`, the lesson preview, `dictSpeak()`, `alphaSay()` — calls `speakText(text, lang)`; don't create `SpeechSynthesisUtterance`s elsewhere. Browsers list their old built-in voices first (Windows: Microsoft Ayumi, Heami, Hanhan…), which sound robotic, so `ttsCandidates(lang)` ranks the device's voices: exact region first, then Edge's neural "Natural" voices, Chrome's online "Google …" voices, other online voices, built-in last (Chinese only matches its own region — zh-HK is Cantonese). Visitors can override the pick per language (`TTS_LANGS`, zh-TW and zh-CN separately) in the settings panel's voice section (`renderTtsSettings`, re-rendered on `voiceschanged` because Chrome loads voices asynchronously); choices are stored by voice name in `localStorage['tts_voices']` and silently fall back to the automatic pick on a device without that voice. Rate is `TTS_RATE` (0.9). `js/speech.js` loads right after the i18n files.

**Recorded audio (`data/audio/`, built by `tools/build_audio.py`)**: Japanese, Korean and Chinese sound robotic in every browser voice, so the JLPT / TOPIK / HSK words, the topic words (`tp_ja_*`, `tp_ko_*`, `tp_zh_*`), the alphabet chart's ja/ko/zh entries and the voice-picker samples are pre-rendered with Google Cloud Text-to-Speech (ja Chirp3-HD-Erinome, ko Chirp3-HD-Kore, zh-CN Chirp3-HD-Leda, zh-TW Wavenet-A — Taiwan Mandarin has no Chirp3 voice; Chirp3 is unreliable on a lone kana / hangul syllable, so those use a Neural2 backup voice). Since 2026-10-08 also French and Russian (all CEFR words, French spoken with its article) and the fr / ru / de / es alphabet tabs, all with Chirp3-HD-Kore (it rolls the Spanish / Russian r properly). One MP3 per text in `data/audio/<ja|ko|zh-CN|zh-TW|fr|ru|de|es>/<id>.mp3`, where id = cyrb53 of the NFC-normalised text in base 36 — `audioId()` in `js/speech.js` and `audio_id()` in the script must stay identical. `index.json` per language lists the files plus aliases (simplified → traditional Chinese; a Japanese kanji word → its most basic reading). Japanese kanji words are keyed `word|kana` and spoken from the kana, because one word can have several readings (一日); `speakWord()` passes the kana as `opts.reading`. `speakText()` plays a recording when the index has one and the visitor hasn't chosen a browser voice for that language, else falls back to `speechSynthesis` (also when `play()` is blocked or the file is missing offline). **Don't edit `data/audio/` by hand**: after changing a word list or the alphabet data, re-run `python tools/build_audio.py` (needs `pip install lameenc` and `GOOGLE_TTS_KEY` in the git-ignored `tools/.google-tts.env`; existing files are kept, so only new texts are rendered; `--audition` builds a page to compare voices). **AI assistant (`js/assistant.js` + `css/assistant.css`, Worker in `worker/assistant/`)**: a floating 小花火 (stand-in until the owner draws a character; desktop: above the settings gear on the right, phones: bottom-left above the tab bar) opens a chat panel. The static site can't hold a key, so messages go to the Cloudflare Worker `hanabi-assistant` (`ASSISTANT_API`; `localhost:8787` when the site runs on localhost), which keeps `GEMINI_API_KEY` as a secret, builds 小花火's persona + the site's feature list in `persona()`, and calls Gemini, trying the models in `MODELS` (wrangler.jsonc) in order, **fastest first** (measured 2026-10-04, time to the first words: gemini-3.6-flash ~0.7 s, 3.5-flash-lite ~0.6 s, 3.8-flash ~5 s, 3.5-flash ~7 s, 3.7-flash often a 503 after 7 s; re-measure if replies get slow). Each flash model's free tier is only **~20 requests a day**; any failure (429 quota, 503, 500, or no answer within `FIRST_BYTE_MS` 5 s) moves on to the next, and a spent (429 per-day) or slow model is skipped for an hour / 10 minutes (`spent`, in isolate memory). The site asks with `stream: true`: the Worker uses `streamGenerateContent?alt=sse`, waits for the first words (an empty stream moves on), then streams plain text that `assistantAsk()` shows as it arrives while 小花火's mouth moves; without `stream` it still answers `{ reply }` JSON (gemini-2.5-* is closed to new keys). Guards: `ALLOWED_ORIGINS`, a rate-limit binding (8/min per IP), 12 turns × 600 chars. The key's Google project (`hanabi-assistant-510517`) has **billing disabled on purpose** so only the free tier is used — with billing linked, Gemini answers 402 "prepayment credits depleted". Local test: key in the git-ignored `worker/assistant/.dev.vars`, then `wrangler dev --port 8787` from that folder (wrangler is installed in the osu project). The chat is kept in sessionStorage; our own error notices are flagged `err` and never sent. When site features change, update the feature list in `persona()`.

## Conventions worth knowing

- No JS framework/module system — everything is global functions/variables attached via plain `<script>` tags, and `onclick="..."` attributes in HTML call these global functions directly.
- Chinese (Traditional) is the default/fallback language throughout (`I18N.zh` is the fallback in `t()`).
- HTML entities (`&#x...;`) are used for CJK/emoji text directly in `index.html` markup instead of raw UTF-8 characters in many places (legacy from earlier edits) — matching surrounding style when editing those sections is fine, but new text can be written as plain UTF-8.

## Workflow for feature/dev requests

For any non-trivial dev request, work through these stages in order:

1. **UI/design pass** (only if the request touches the front end): match the 和紙/墨夜 theme — flat cards, chunky 3D buttons, the CSS custom properties in `css/theme.css` (don't hardcode colors; check both themes), the phone layout (≤768px: bottom tab bar, no top nav), and the existing per-feature `css/*.css` split. There's no React/Tailwind/v0 in this project — new UI is plain HTML + CSS, written by hand.
2. **Implementation**: wire up the HTML/CSS/JS following the conventions above (global functions, `onclick=` handlers, i18n keys added to all 9 `i18n/<lang>.js` files, new files registered in `index.html`'s script/link tags and `service-worker.js`'s `ASSETS`).
3. **Verification** (this project has no test suite or build step, so "testing" means): check the changed files for obvious syntax errors, then actually load the change in a browser (e.g. `python -m http.server` from the repo root) and click through the affected feature before calling it done — per the top-level guidance to verify UI changes in a real browser rather than assuming they work.
4. **Final report**: once verified, and after committing/pushing per the user's request, give a short summary of what changed — don't pad it with restated context.
